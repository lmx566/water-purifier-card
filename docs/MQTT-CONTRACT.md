# WATER MQTT compatibility contract

Source reviewed on **2026-11-03**: `main/mqtt_model.hpp` and `main/mqtt_service.cpp` in the parent firmware project. This describes source, not a live-device or release acceptance result. The card consumes HA entities; it neither connects to MQTT nor polls the ESP32 directly.

## Discovery and availability

- Device identifier: `water_<12 lowercase hexadecimal STA MAC digits>`.
- Discovery: `homeassistant/sensor/<device-id>/<key>/config`.
- Telemetry: `water/<device-id>/state`; availability: `water/<device-id>/availability`.
- Unique ID: `<device-id>_<key>`, with `{{ value_json.<key> }}` as value template.
- All entries, including UV, use HA's **sensor** domain. No switch or binary-sensor discovery is generated by this source.
- Discovery and availability are retained, QoS 1. Telemetry is QoS 1, not retained, normally about every ten seconds after discovery and when the outgoing queue is clear.
- `expire_after: 45` and the retained offline last will provide availability handling. Discovery is resent on connection and HA birth, subject to firmware rediscovery throttling.

HA assigns entity IDs, which can be renamed or receive collision suffixes. The card resolves exact unique IDs within the selected device registry entry. It must not construct IDs from a MAC or treat the HA registry ID as the firmware device ID.

This card revision does not automatically render every discovered entity. Its circuit is a configured direct-flow schematic, not proof of a controller's physical topology.

Water totals use `total_increasing`; flow/recovery use `measurement`. Most non-flow entries are diagnostic sensors. Cumulative totals must not be labeled “Today” without a distinct period-based data source.

## Filter reminder semantics

The eight slots report:

| Value | Meaning |
| --- | --- |
| `not_fitted` | Filter descriptor is not present |
| `disabled` | Reminder plan is disabled; the filter may still be installed |
| `not_installed` | No installation record for the reminder |
| `due` | Runtime or calendar limit reached |
| `calendar_unknown` | Calendar reminder cannot currently be evaluated |
| `within_limits` | Evaluated reminder limits have not been reached |
| `unknown` | Maintenance data is stale |

The MQTT payload does not provide the catalog's display name, filter kind, position, remaining percentage, or days remaining. Eight reminder slots do not imply a fixed filter-stage order. The card may omit `not_fitted` automatic reminders, but must retain `disabled` as a distinct state. Custom names and `stage` associations are user configuration.

## UV semantics

- `uv_enabled`: `enabled`, `disabled`, or `unknown` when configuration storage is unhealthy.
- `uv_command`: `commanded_on`, `off`, or `unknown` when control/UV evaluation is not fresh enough.
- `uv_status`: `disabled`, `configuration_required`, `feedback_unavailable`, `commanded_on`, `off`, `unavailable`, or a UV fault identifier.

A command reports the controller's output mask, not an optical measurement. Voltage/current do not establish lamp on/off, UV intensity, or water disinfection. A valid disabled setting can hide the UV symbol; an unknown mapped state must not silently turn into “off.”

## Other hardware and missing values

There are no dedicated discovered entities for pump/inlet/waste-valve commands, pressure, or wet/dry leak input in this source. The card's optional roles for these need a separately supplied entity with the stated meaning.

Telemetry contains `armed`, `commanded_mask`, and `leak_bypassed`, but they have no corresponding discovery entity here. `leak_bypassed` describes a bypass configuration, not detected leakage. No command mask or current value should be relabeled as physical valve feedback.

Invalid or stale numeric measurements are sent as JSON null. Flow totals also depend on healthy totals storage. Recovery is undefined without sufficient valid flow information. The card displays missing/unavailable/unknown data rather than zero or invented history.

Controller phases include `locked`, `idle`, `preparing`, `preflush`, `producing`, `postflush`, `fault`, `maintenance`, `flushing`, and `testing`. Fault identifiers can expand across firmware releases; readable fallbacks must preserve the reported identifier rather than hide an unknown fault.

## History and commands

The graph uses the mapped TDS entity's Home Assistant history. It is independent of the controller's own flash history and has no access to it through MQTT. History availability follows HA Recorder, retention, and permissions. Current readings should still work if history is absent.

The firmware subscribes only to HA birth for this integration. It has no MQTT device-control command subscription; the card calls no HA control service. More-info opens entity details; the dashboard link opens a page. Future controls require a separate command/result/interlock contract.

Broker provisioning belongs to the firmware and HA MQTT integration. The card stores no broker credentials. See [Home Assistant MQTT](https://www.home-assistant.io/integrations/mqtt/) and the [HA history REST API](https://contributors.home-assistant.io/core/internals/rest-api/) for host behavior.
